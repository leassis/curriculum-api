# Structured Resume Specification

**Approved**: 2026-11-23 - user: "Approved, no download"

**Depends on**: `tailored-resumes`, `resume-custom-instructions`, `resume-create-flow` (merged). Blocks: `honest-assessment`. Touches: `src/db/schema.ts` + one migration (serialized on `main`, AD-003), a new `src/services/tailor/` (Resume Document schema, Master CV parser, renderers, assembler), `src/services/resume.service.ts`, `src/services/llm.service.ts` (structured generate), `src/repositories/{resume,recruiter-chat}.repository.ts`, `src/services/recruiter-chat.service.ts`, `src/admin/resumes/{routes.ts,view.tsx,client.ts}`, print view, `GLOSSARY.md`, their tests.

## Problem Statement

A Tailored Resume is one markdown text. Code cannot tell a role from a bullet, so it cannot lay the resume out differently (custom PDF versions), cannot hold the model to the CV's roles, titles and dates, and cannot report what was cut. Tailored Resumes move to JSON only: a Resume Document of sections and items, generated by the model item by item against the Master CV, edited through a form, and rendered to Print View, markdown download and recruiter-chat context. Markdown stays only for the Master CV, which is parsed into items.

## Goals

- [ ] Every generated Tailored Resume is stored as a valid Resume Document and nothing else.
- [ ] The model rewrites item text and bullets only; every heading line in a generated resume is copied by code from the Master CV.
- [ ] The Owner edits headings, text and bullets, removes and reorders items, without seeing markdown or raw JSON.
- [ ] Print View, markdown download and recruiter chats show the same resume the editor shows.

## Out of Scope

| Feature | Reason |
| ------- | ------ |
| Custom PDF layouts | Future feature the JSON enables |
| Converting existing markdown resumes | User: "Drop them" |
| Master CV as JSON or a structured Master CV editor | User: phasing out markdown is for resumes only (AD-006) |
| Score, missing skills, omissions, restoring dropped roles | `honest-assessment` |
| Adding new sections or items in the editor | Generated resumes come from the Master CV; the Owner edits and removes |
| Raw JSON editing | User chose the structured form |
| Model reordering items | Source order (honest-assessment answer, kept here) |

## User Stories

### P1: Generate a Resume Document ⭐ MVP

**User Story**: As the Owner, I want Generate to produce a structured resume from my Master CV, so that the resume can be laid out freely and its headings stay true.

**Why P1**: Nothing else exists without a stored Resume Document.

**Acceptance Criteria**:

1. WHEN Generate runs THEN the system SHALL parse the Master CV per the parsing rule and send the model each section and item with its id, kind and heading.
2. WHEN Generate runs THEN the system SHALL call the model through the `ai` SDK structured output with the zod schema `TailorOutputSchema`, each field carrying a `.describe()` text, and SHALL accept only a reply that parses against it.
3. WHEN the model returns valid output THEN the system SHALL store a Resume Document assembled in source order whose section titles, kinds and item headings equal the parsed source character for character.
4. WHEN the model leaves an item id out THEN the stored document SHALL not contain that item.
5. IF the output fails the schema, names an unknown id or names an id twice THEN the system SHALL call the model once more with the same input.
6. IF the second call also fails per AC 5 THEN the system SHALL answer 502 "Generation failed, try again" and SHALL leave `structured` and `model` unchanged.
7. IF the Master CV has no `## ` heading THEN Generate SHALL answer 400 "Structure the master CV with ## sections and ### items" and SHALL not call the LLM.
8. IF a returned string starts with 1-6 `#`, `- ` or `* ` followed by a space THEN the system SHALL store it without that prefix.
9. WHEN Custom Instructions are non-empty THEN the tailor input SHALL wrap them in `<custom_instructions>`…`</custom_instructions>` under the existing preamble, with both tags removed from the text first (AD-007).
10. WHEN Custom Instructions are empty THEN the tailor input SHALL contain no `<custom_instructions>` tag.
11. The system SHALL send the model no Personal Info Field value and no `profile.fullName`.
12. IF the Master CV contains `profile.fullName` (case-insensitive) THEN Generate SHALL answer 400 "Your full name is in the master CV — it is added when printed" and SHALL not call the LLM.
13. IF a `### ` heading of the Master CV is empty or longer than 200 characters THEN Generate SHALL answer 400 "A ### heading in the master CV is empty or longer than 200 characters" and SHALL not call the LLM.
14. WHEN a returned or saved text field has a line starting with 1-6 `#`, `- ` or `* ` followed by a space THEN the system SHALL store that line without the prefix.
15. WHEN a returned or saved heading or bullet contains line breaks THEN the system SHALL store it with each line break replaced by one space.

**Independent Test**: Mock model returns text for two of three items with altered heading text in a body: stored document has source headings, two items, source order.

### P1: Store JSON only ⭐ MVP

**User Story**: As the Owner, I want resumes stored as JSON only, so that there is one source of truth.

**Why P1**: AD-008.

**Acceptance Criteria**:

1. The migration SHALL add `structured jsonb NULL` to `tailored_resumes`, drop `content`, and set `model` to NULL on every existing row.
2. WHEN the migration runs on a database with tailored resumes THEN every row SHALL keep its id, title, company, Job Description, Custom Instructions, header fields and recruiter-chat links.
3. WHEN a resume is created THEN `structured` SHALL be NULL until its first successful generation.
4. The system SHALL define the Resume Document once as the zod schema `ResumeDocumentSchema`, and the `ResumeDocument` type SHALL be inferred from it.
5. WHEN Generate assembles a document or Save builds one from the form THEN the service SHALL parse it with `ResumeDocumentSchema` before writing.
6. IF a document fails `ResumeDocumentSchema` on Save THEN the service SHALL answer 400 naming the first failing field path and store nothing.
7. IF an assembled document fails `ResumeDocumentSchema` on Generate THEN the system SHALL treat it as a schema failure (Generate AC 5-6).
8. WHEN the repository reads a row with non-NULL `structured` THEN the service SHALL parse it with `ResumeDocumentSchema`.
9. IF a stored `structured` value fails `ResumeDocumentSchema` on read THEN the service SHALL log error `stored resume document invalid` with the resume id and the failing path, and the editor SHALL show "This resume's stored data is invalid; generate it again" with the Generate button and no form.

**Independent Test**: Integration: insert a row before migration, migrate, row kept with `structured` NULL and no `content` column.

### P1: Edit the Resume Document ⭐ MVP

**User Story**: As the Owner, I want to edit headings, text and bullets, remove and reorder items, so that I fix the draft without touching markdown or JSON.

**Why P1**: The Owner must be able to correct a generated resume.

**Acceptance Criteria**:

1. WHEN `GET /admin/resumes/:id` is requested and `structured` is not NULL THEN the editor SHALL show, per section, its title and a text field, and per item a heading field, a text field and a bullets field holding one bullet per line.
2. WHEN `GET /admin/resumes/:id` is requested and `structured` is NULL THEN the editor SHALL show "Not generated yet" and the Generate button and no section form.
3. WHEN the Owner uses "Save" THEN the system SHALL store the Resume Document built from the form (empty bullet lines ignored) and show "Saved".
4. WHEN the Owner uses "Remove" on an item THEN the item SHALL disappear from the form and, after "Save", from the stored document.
5. WHEN the Owner uses "Move up" or "Move down" on an item THEN the item SHALL swap with its neighbour in the same section, and "Save" SHALL store the new order.
6. IF any saved string contains a Personal Info Field value THEN Save SHALL answer 400 "Your <label> is in the body — keep contact data in Personal info" and store nothing.
7. IF an item heading is empty or a bound is exceeded THEN Save SHALL answer 400 from `ResumeDocumentSchema` naming the failing field path (Store AC 6) and store nothing.
8. WHEN the form's values change THEN the preview SHALL show the rendered HTML of the current values.
9. WHEN Generate succeeds from the editor THEN the swapped editor SHALL show the new document in the form.

**Independent Test**: Load a stored document, remove one item, move another up, change a bullet, Save; reload shows the changes.

---

### P1: Outputs from JSON ⭐ MVP

**User Story**: As the Owner, I want print, download and recruiter chats to use the Resume Document, so that every output matches the editor.

**Why P1**: Removing markdown would otherwise break them.

**Acceptance Criteria**:

1. The system SHALL render a Resume Document to markdown as: per section `## <title>` (none for `intro`), its text, then per item `### <heading>`, its text and `- <bullet>` lines, in stored order.
2. WHEN the Print View of a resume is requested THEN its body SHALL be the HTML of that markdown, with the Personal Header as today.
3. WHEN the markdown download is requested THEN its body SHALL be the Personal Header lines followed by that markdown.
4. WHEN a recruiter chat linked to a resume streams THEN the Career Body sent SHALL be that markdown.
5. IF the linked resume's `structured` is NULL THEN the recruiter chat SHALL use the Master CV (today's fallback for empty content).
6. WHEN the Print View or download is requested for a resume with `structured` NULL THEN it SHALL show the existing empty state.

**Independent Test**: Store a document; Print View, download and recording mock recruiter context all contain each heading and bullet.

## Edge Cases

- WHEN two items have the same heading THEN they SHALL keep distinct ids and be assembled independently.
- WHEN a section has no `###` items THEN its lead text SHALL be its only content.
- WHEN the Owner removes every item of a section and its text is empty THEN Save SHALL drop the section.
- IF a bullets field holds only blank lines THEN the item SHALL be stored with `bullets: []`.
- WHEN the Owner empties a text-only section and then uses Remove, Move up or Move down on an item in a later section THEN the op SHALL act on the item whose button was used.

Dimensions sweep (Large):
- Input validation & bounds → Store AC 4-9, Edit AC 6-7, bounds in Assumptions.
- Failure states → Generate AC 6-7.
- Idempotency / retry → Generate AC 5; Save overwrites (last wins).
- Auth & rate limits → existing admin auth on `/admin/*`; no new route.
- Concurrency → N/A because single Owner, last write wins as today.
- Data lifecycle → Store AC 1-2 (generated texts discarded once, rows kept).
- Observability → retry logs warn `tailor output rejected` with reason `schema`, `unknown_id` or `duplicate_id`, no content.
- External-dependency failure → Generate AC 6.
- State transitions → Store AC 3, Edit AC 2.
